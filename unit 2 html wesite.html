Abstract

Food wastage is a practical problem in homes, hostels, canteens, restaurants and events. This project proposes a simple website through which food donors can list surplus edible food and authorised recipient organisations can express interest in collecting it. The website records food details, quantity, pickup location, availability time and status. The proposed solution aims to improve coordination, reduce avoidable waste and make surplus-food redistribution easier. This report contains the Software Requirements Specification (SRS), system design, implementation plan, testing approach and sample web-page implementation.

1. Introduction

Food wastage occurs when edible food is discarded or remains unused despite being potentially useful to others. Surplus food may be available at canteens, restaurants, functions and households, while community groups may be able to redistribute it. A central website can help connect these groups and provide a clear record of available food and collection status.

Purpose

To design and demonstrate a responsive client-side website that organises surplus-food listings and helps donors and recipients coordinate collection.

Definitions

Donor
A person or organisation offering surplus food.
Recipient
An organisation or authorised person requesting a listing.
Listing
A record containing food details and pickup information.
Responsive design
A layout that adapts to different screen sizes.

2. Problem Statement and Objectives

Surplus food information is often shared informally, which can lead to delays, missed collections and limited visibility. The proposed website provides a single interface to publish and browse available food listings.

Objectives

  • Provide a simple form to add a surplus-food listing.
  • Display available listings in a readable, searchable layout.
  • Capture quantity, food category, pickup location and availability time.
  • Allow users to mark a listing as requested or collected in the demonstration.
  • Use semantic HTML, responsive CSS and JavaScript DOM/event handling.
  • Demonstrate basic version-control practices with Git and GitHub.

3. Scope and Feasibility

Project Scope

The academic prototype focuses on the user interface and client-side behaviour. It can add listings, filter them by keyword/category and update their status during a browser session. A production deployment would require a backend, database, secure user accounts and operational procedures.

Feasibility

  • Technical: HTML5, CSS3 and JavaScript are sufficient for a working front-end prototype.
  • Economic: the prototype can be developed using free tools and a standard computer.
  • Operational: the forms and listing cards are designed for users with basic web familiarity.
  • Schedule: the work can be completed in stages — requirements, design, coding, testing and documentation.

4. Software Requirements Specification (SRS)

Functional Requirements

Functional requirements
IDRequirement
FR-01The system shall allow a donor to enter food name, category, quantity, pickup location and available-until time.
FR-02The system shall validate required fields before adding a listing.
FR-03The system shall display active listings as cards.
FR-04The system shall filter listings using a keyword and category.
FR-05The system shall allow a listing status to be changed to Requested or Collected.
FR-06The system shall show a clear message when no listing matches the filter.

Non-Functional Requirements

  • Usability: clear labels, readable text and straightforward navigation.
  • Accessibility: semantic headings, labels associated with inputs and keyboard-friendly controls.
  • Responsiveness: usable on desktop, tablet and mobile screens.
  • Reliability: invalid or incomplete form entries should not create listings.
  • Maintainability: separate HTML, CSS and JavaScript files.
  • Privacy and safety: a real deployment must protect user data and avoid publishing sensitive personal information.

Hardware and Software Requirements

Hardware: computer or laptop, keyboard, mouse/touchpad and internet access for optional hosting.

Software: modern web browser, text editor (such as Visual Studio Code) and Git. The prototype uses HTML5, CSS3 and vanilla JavaScript; no paid software is required.

5. System Design

Architecture

For the prototype, the browser renders the HTML interface, CSS controls presentation and JavaScript validates forms, filters listings and updates status. Listing data is held in memory for the current session; it is not shared across users.

Donor / Recipient → Web Interface (HTML) → JavaScript Validation & Filtering → Listing Cards and Status

Data Model

Listing data model
FieldDescription

foodNameName or description of the food

availableUntilCollection deadline
statusAvailable, Requested or Collected

Use Cases

  • Donor adds a listing and checks the details before submission.
  • Recipient browses and filters currently available listings.
  • Recipient marks an appropriate listing as Requested.
  • After collection, the listing is marked Collected so it is no longer treated as available.

6. Implementation Plan and Web Interface

Technologies

HTML5 provides the structure and accessible form controls. CSS3 provides responsive layout, spacing, colours and card styling. JavaScript (ES6+) handles form submission, validation, DOM updates and filtering. Git/GitHub can be used to track changes and maintain project versions.

Main Pages / Sections

  • Home: introduces the purpose of the website.
  • Login / Sign Up: forms for registering and signing in as a donor, recipient or administrator.
  • Add Food: form for creating a surplus-food listing.
  • Available Food: cards containing food details and status actions.
  • About / Contact: explains the project and provides a contact method in a production version.

Core Interaction Flow

  1. Open the website in a browser.
  2. Enter the food details in the Add Food form.
  3. Submit the form; JavaScript checks required fields.
  4. A valid listing appears in the available-food section.
  5. Use the search/filter controls to find a listing.
  6. Update its status when it is requested or collected.
Implementation note: This report specifies the front-end behaviour and file structure. The prototype must be coded and tested in the listed files before claiming a live, fully deployed system.

8. Limitations and Future Enhancements

Limitations

  • Data is stored only in the current browser session and is not synchronised between users.
  • No real authentication, database, donor verification, notifications or map integration is included in the front-end design.
  • Food safety, collection, transport and recipient eligibility require real-world procedures beyond the website.

Future Enhancements

  • Add a backend API and database for persistent listings.
  • Introduce secure sign-in and role-based permissions.
  • Add recipient verification, collection confirmations and email/SMS notifications.
  • Integrate maps for pickup coordination and provide an administrator dashboard.
  • Use the Fetch API to load and update JSON data from a server.

9. Conclusion

The Food Wastage Management Website is a practical full-stack foundations project that applies semantic HTML, responsive CSS and JavaScript interaction to a community problem. Its requirements and design define a clear path from food listing creation to collection status updates. The front-end prototype can be extended with a secure backend and database to support real multi-user coordination.
